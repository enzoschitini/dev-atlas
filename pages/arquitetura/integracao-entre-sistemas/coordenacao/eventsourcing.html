Event sourcing

Em vez de guardar só o estado atual, guarda-se cada mudança como um evento imutável.

Simulação

Mexa nos controles e aperte os botões para ver o padrão funcionando, inclusive quando algo dá errado.

Como funciona

O estado é derivado: para saber o saldo, soma-se todos os depósitos e saques. Eventos só são acrescentados, nunca alterados. Isso dá auditoria completa, “viagem no tempo” (como estava na terça?) e a possibilidade de criar novas visões reprocessando o histórico. Snapshots periódicos evitam reler tudo. É frequentemente combinado com CQRS.

Passo a passo

  1. Um comando é validado contra o estado atual
  2. O resultado vira um evento imutável, acrescentado ao log
  3. O estado é reconstruído aplicando os eventos em ordem
  4. Projeções e consumidores reagem aos novos eventos

Quando usar

  • Auditoria e rastreabilidade completas
  • Reconstruir ou corrigir estado reprocessando eventos
  • Novas projeções sem migrar dados
  • Depurar reproduzindo exatamente o que aconteceu

Quando evitar

  • Aumenta a complexidade de consulta e de versionar eventos
  • Apagar dados pessoais (LGPD) é difícil com log imutável
  • CRUD simples não precisa disso

Exemplos

  • Contas bancárias e livros contábeis (ledgers)
  • Pedidos em que o histórico importa: quem alterou e quando
  • Controle de versão: o Git é, em essência, um log de mudanças

Tecnologias

EventStoreDB, Axon, Kafka, Marten, PostgreSQL
