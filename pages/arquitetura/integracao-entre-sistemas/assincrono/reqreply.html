Request-reply assíncrono

O pedido vai por uma fila e a resposta volta por outra, ligadas por um identificador de correlação.

Simulação

Mexa nos controles e aperte os botões para ver o padrão funcionando, inclusive quando algo dá errado.

Como funciona

O cliente envia a mensagem para uma fila de requisições, com um correlation ID e o endereço da fila onde espera a resposta. O worker processa e publica o resultado na fila de respostas com o mesmo ID, e o cliente casa as duas pontas. Dá o desacoplamento das filas mantendo o jeito “pergunta e resposta”. Uma variação comum em HTTP: responder 202 Accepted e oferecer um endpoint de status (ou um webhook) para avisar quando terminar.

Passo a passo

  1. Cliente publica o pedido com correlation_id e reply-to
  2. Um worker consome e processa (pode demorar)
  3. Worker publica a resposta na fila indicada, com o mesmo ID
  4. Cliente recebe e relaciona com o pedido original

Quando usar

  • Operações demoradas sem manter conexão HTTP aberta
  • Balancear carga entre vários workers
  • Isolar o cliente de falhas do processador

Quando evitar

  • Se uma resposta rápida resolve, request-response é mais simples
  • Sem timeout, o cliente não sabe o que fazer se a resposta nunca chegar
  • Mais peças e mais estados para acompanhar (pedido pendente, concluído, falhou)

Exemplos

  • Geração de relatório pesado: pede agora, recebe quando pronto
  • Antifraude de pagamento que leva alguns segundos
  • Processamento de vídeo ou IA: o app mostra “processando…” e atualiza ao fim

Tecnologias

RabbitMQ (reply-to), Amazon SQS, Kafka, JMS, HTTP 202
