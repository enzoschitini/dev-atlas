Pub/Sub

Um publicador emite um evento num tópico; todos os assinantes interessados recebem uma cópia.

Simulação

Mexa nos controles e aperte os botões para ver o padrão funcionando, inclusive quando algo dá errado.

Como funciona

O publicador não sabe quem vai receber: só publica no tópico. Cada assinante tem a sua própria “caixa” e recebe uma cópia de cada mensagem, processando de forma independente. Novos interessados entram sem mexer no publicador, o que reduz o acoplamento. Na prática, costuma-se combinar com filas: cada assinante lê de uma fila própria ligada ao tópico.

Passo a passo

  1. Publicador envia o evento ao tópico (ex.: pedido.criado)
  2. O broker copia o evento para cada assinatura
  3. Cada assinante processa por conta própria
  4. A falha de um assinante não afeta os demais

Quando usar

  • Um evento, vários interessados, sem acoplamento direto
  • Adicionar novos consumidores sem alterar quem produz
  • Propagar mudanças de estado entre serviços e domínios

Quando evitar

  • Quando é preciso resposta direta do destinatário
  • Eventos mal definidos viram confusão entre equipes: trate-os como contrato
  • Rastrear “quem reagiu a quê” fica mais difícil (exige tracing)

Exemplos

  • Pedido criado → estoque reserva, financeiro cobra, CRM atualiza, analytics registra
  • Notificações push para muitos dispositivos
  • Invalidação de cache distribuído

Tecnologias

Google Pub/Sub, Amazon SNS, Kafka, RabbitMQ (topic/fanout), Redis Pub/Sub, NATS
